## 2. 原生树实测契约

以下数据来自原生文件浏览器，不是推断：

| 项目 | 实测 |
| --- | --- |
| 行高 | `24.9px` |
| 行距 | `margin-bottom: 2px` |
| 缩进 | 每层 17px；实际内容缩进由行内 padding 承担，不是子容器宽度 |
| 作用域偏移 | 原生树里沙箱自身占一层，所以沙箱子项内容 x 是 97px；单库树隐藏库根后，同一项内容 x 应为 80px（左移一层 17px） |
| 文件夹落点 | 0.27 → before；0.50 → inside；0.73 → after（30/40/30） |
| 文件落点 | 0.2 → before；0.8 → after（50/50） |
| 2px 缝隙 | 有落点，按最近行 + 方向解析 |
| 右侧留白 | 有落点；在沙箱根上会解析到库根 |
| 鼠标选中 | 单击打开并加 `.is-active`；Alt+单击切换 `.is-selected`；Shift+单击范围选中 |
| Ctrl/Cmd+单击 | 在新标签页打开 |
| 文件右键菜单 | 在新标签页中打开、在新标签组中打开、在新窗口中打开、创建副本、将文件移动到…、复制路径、使用默认应用打开、在系统资源管理器中显示、置顶、隐藏、重命名、删除 |
| 文件夹右键菜单 | 新建笔记、新建文件夹、创建副本、将文件夹移动到…、在文件夹中查找、复制路径、在系统资源管理器中显示、排序方式、置顶、隐藏、重命名、删除 |
| 键盘 | 树容器获得焦点后，方向键移动焦点；F2 进入行内重命名，Esc 退出 |
| 附件 | 原生显示 `附件.png`，行文本为 `附件`（扩展名不进入标题文本） |

一个容易误判的点：原生树**不是任何位置都只渲染视口附近的行**。实测 10,000 条时：

- 顶部：约 40 个 DOM 行；
- 直接跳到底部：约 9,984 个 DOM 行；
- 原生自身在“跳到底部”这个动作上也会保留大量行。

因此 P3 的验收不能写成“底部 DOM ≤200”，应写成“顶部/常规滚动窗口受控，底部不劣于原生同场景”。

## 4. 用例结果

### 4.1 t17 拖拽对等

结果：`17/21 PASS，4 PENDING，0 FAIL`。原生基准 12/12 全 PASS。

PENDING：

1. 文件夹 0.27 before / 0.5 inside / 0.73 after
2. 移入文件夹落到末尾
3. 树内空白把 A1 移回库根
4. 行几何与原生一致（单库比原生少一层库文件夹，内容整体左移 17px）

当前已 PASS 的单库项：文件 50/50、2px 缝隙、右侧留白、非自定义排序切 custom、拖后无残留移动。

### 4.2 t18 交互对等

结果：`11/18 PASS，7 PENDING，0 FAIL`。原生基准 9/9 全 PASS。

PENDING：

1. 附件/非 md 显示
2. Alt+单击选中且不打开
3. Shift+单击范围选中
4. 文件右键菜单包含完整核心项
5. 文件夹右键菜单包含新建/排序/置顶/隐藏（缺创建副本、将文件夹移动到…、在文件夹中查找）
6. F2 行内重命名
7. 单库树不再有全库排序入口

当前已 PASS 的单库项：单击打开与高亮、Ctrl+单击开新标签。

### 4.3 t19 性能对等

#### 10,000 条（最终脚本）

结果：`4/5 PASS，1 PENDING，0 FAIL`。

| 指标 | 原生 | 单库 |
| --- | --- | --- |
| 造数耗时 | — | 194,292 ms（vault.create，插件排序事件暂停，单库树关闭） |
| 打开/展开耗时 | 2,002.6 ms（展开 10k 子项） | 2,668 ms（打开单库树并渲染） |
| 顶部 DOM 行数 | 40 | 10,000 |
| 跳到底部 DOM 行数 | 9,984 | 10,000 |
| 顶部 scrollHeight | 269,766 px | 269,012 px |

PENDING：单库树顶部只渲染视口附近的行。

单库打开耗时是原生的约 1.33 倍，仍在 P0 设定的同一数量级内；但顶部 DOM 行数没有窗口化，这是 P3 要解决的核心差异。底部单库 10,000 行不劣于原生 9,984 行，因此不再把“底部 ≤200”作为门槛。

#### 300 条（快速回归样本）

结果：`3/5 PASS，2 PENDING，0 FAIL`。

| 指标 | 原生 | 单库 |
| --- | --- | --- |
| 打开/展开耗时 | 44.8 ms | 23 ms |
| 顶部 DOM 行数 | 40 | 300 |
| 底部 DOM 行数 | 48 | 300 |

300 条时原生底部只保留 48 行，单库 300 行；10,000 条时原生的底部跳转反而保留 9,984 行。这个差异说明“原生虚拟列表”不是固定的窗口大小，P3 必须用同一条用例在多个规模上比较，不能只看某个固定行数阈值。

## 5. 运行命令

```bash
# 拖拽对等
node scripts/cdp/run.mjs scripts/cdp/t17-tree-parity-dnd.mjs

# 交互对等
node scripts/cdp/run.mjs scripts/cdp/t18-tree-parity-interactions.mjs

node scripts/cdp/run.mjs scripts/cdp/t19-tree-perf.mjs

```

前置条件与现有 CDP 用例相同：Obsidian 带 `--remote-debugging-port=9223` 启动，打开测试 vault。

## 6. 测试隔离与清理

- t17/t18 使用 `__kb统一自测__`，t19 使用 `__kb性能自测__`；用例开始前删除并重建，结束后删除文件夹和对应 `order.items` 键。
- t19 造数前会关闭单库树；否则每批 `vault.create` 都会触发树重绘，10k 造数会被拖到十分钟以上（P0 实际踩到）。
- 10k 运行结束后已核对：两个沙箱文件夹不存在、文件数 0、设置残留 0、单库树叶子 0。
- 测试期间 Obsidian 控制台可能出现删除后读取文件的 ENOENT；它来自测试沙箱删除和 Obsidian 延迟读，不是生产代码异常。
- P0 未修改任何生产代码、版本号和已发布内容。

## 7. 风险与后续

1. **原生行为差异**：原生底部跳转的大量渲染说明不能用统一 DOM 行数阈值套两棵树；P3 用“同规模、同操作”对比。
2. **F2 焦点**：原生 F2 需要文件树容器获得焦点（不是仅点击行）；单库树 P4 实现时必须复刻焦点管理。
3. **作用域缩进**：原生沙箱子项与单库库根子项天然差一层 17px；验收用“单库内容 x = 原生同项 - 17px”，不要直接比较绝对 padding。
4. **测试规模**：10k 造数约 3 分钟、清理有延迟读取噪音；日常用 300 快跑，发布前再跑 10k。
5. **待纳入总回归**：t17 在 P2 转绿后加入 `run-all.mjs`；t18 在 P4 转绿后加入；t19 在 P3/P5 根据窗口化结果加入。
